# Compito 684 (ArtifactsBench) — materiali di valutazione (approvati il 23 ott 2026)

Fonte: `684.json`, testo originale:
> Create a file tag management platform where users can upload files and add multiple tags (such as 'work', 'important', etc.) to each file, supporting quick filtering of files by tags.

Cosa cambia rispetto alla bozza con tetto 8:
- marcatore `file-name`: i passi riconoscono un file dal suo nome esatto, non da «il testo del contenitore contiene»
  (prima `relazione.pdf` e un eventuale `nota.txt (4 B)` si confondevano poco, ma il controllo era fragile);
- marcatori `file-delete` e `tag-remove`: la cancellazione del file e la rimozione di un'etichetta, che il contratto
  copre gia' per regola del protocollo (CRUD sempre, «es. cancellare un file in `684`»), ora hanno anche un passo
  d'interfaccia (sistema proattivo); il vecchio dubbio 1 (DELETE si' o no) e' chiuso dal protocollo;
- i passi preparati via rotte seguono la regola «non valutabile» (22 ott), che la bozza precedente non applicava.

## 1. Riassunto e interpretazione minima

- Piattaforma web per caricare file sul server e vederli in una lista.
- A ogni file caricato si aggiungono piu' etichette di testo libero (es. `work`, `important`).
- La lista si filtra per etichetta: scelta un'etichetta, restano visibili solo i file che la portano.

Interpretazione minima dei punti vaghi:
- **«upload files»**: un file per volta basta; nessun limite di tipo o dimensione richiesto (lo script usa file di
  pochi byte: `.txt`, `.png`, `.pdf`). Trascinamento, barre di avanzamento, anteprime: non richiesti.
- **«add multiple tags»**: si aggiungono etichette a un file gia' caricato; etichette al momento del caricamento non
  richieste. Rinominare etichette, colori, gerarchie: non richiesti.
- **«quick filtering by tags»**: filtro per **una** etichetta alla volta, piu' un comando per tornare a tutti i file.
  AND/OR, ricerca per nome, filtri per data o tipo: non richiesti (voci della checklist 2, non del testo).
- **Persistenza**: non nominata, ma implicita in «platform» con caricamento; la fissa il contratto (formato).
- **Cancellare un file / togliere un'etichetta**: non nel testo; entrano per la regola del sistema proattivo
  (contratto CRUD sempre). Nell'interfaccia sono marcatori in piu' e due passi (12 e 13): vedi dubbio 1.

## 2. Contratto delle rotte

Formato: JSON con `Content-Type: application/json`, tranne il caricamento (`multipart/form-data`) e il contenuto del
file (byte grezzi). Oggetto file:

```json
{"id": "<stringa o intero, univoco>", "name": "nota.txt", "size": 4, "tags": ["work", "important"]}
```

`tags` e' un elenco senza duplicati, ordine libero. Un'etichetta e' una stringa non vuota dopo aver tolto gli spazi
iniziali e finali; il server la salva ripulita. Maiuscole e minuscole: distinte (`Work` != `work`).

| Metodo | Percorso | Corpo della richiesta | Risposta (successo) | Errori |
|---|---|---|---|---|
| POST | `/api/files` | multipart, campo `file` (un file) | `201`, oggetto file con `name` = nome originale, `size` in byte, `tags: []` | `400` se manca il campo `file` |
| GET | `/api/files` | - | `200`, elenco di oggetti file (anche `[]`) | - |
| GET | `/api/files?tag=<etichetta>` | - | `200`, solo i file con quell'etichetta (corrispondenza esatta) | - |
| GET | `/api/files/{id}` | - | `200`, oggetto file | `404` id inesistente |
| GET | `/api/files/{id}/content` | - | `200`, byte identici a quelli caricati | `404` id inesistente |
| PUT | `/api/files/{id}/tags` | `{"tags": ["work", "important"]}` (sostituisce l'elenco intero; `[]` toglie tutte le etichette) | `200`, oggetto file aggiornato, duplicati tolti | `400` se `tags` manca, non e' un elenco o contiene un elemento non stringa o vuoto; `404` id inesistente |
| DELETE | `/api/files/{id}` | - | `204` senza corpo; file e metadati rimossi | `404` id inesistente |

**Persistenza.** Metadati in `data/files.json` oppure `data/app.db` (SQLite) nel workspace; contenuto dei file in
`data/uploads/`. Tutto sopravvive al riavvio di `start.sh`. Non si vincolano i nomi dei file dentro `data/uploads/`
ne' la struttura interna del server.

## 3. Marcatori data-testid (11 su 12)

| Marcatore | Elemento |
|---|---|
| `upload-input` | l'`<input type="file">` con cui si sceglie il file |
| `upload-submit` | il pulsante che avvia il caricamento del file scelto |
| `file-item` | contenitore di un file nella lista (uno per file) |
| `file-name` | dentro ogni `file-item`: il nome del file; testo = nome originale esatto |
| `file-delete` | dentro ogni `file-item`: comando che cancella quel file |
| `tag-input` | dentro ogni `file-item`: campo di testo per una nuova etichetta |
| `tag-add` | dentro ogni `file-item`: pulsante che aggiunge l'etichetta scritta in `tag-input` |
| `file-tag` | dentro il `file-item`: ogni etichetta del file; testo = nome dell'etichetta (vedi `tag-remove`) |
| `tag-remove` | dentro ogni `file-tag`: comando che toglie quell'etichetta dal file |
| `filter-tag` | un comando di filtro per ciascuna etichetta esistente; testo = nome dell'etichetta |
| `filter-clear` | comando che toglie il filtro e mostra tutti i file |

Nota per il prompt: il testo di `file-tag` si confronta dopo aver tolto il testo di `tag-remove` e gli spazi (cosi'
un `×` dentro la pillola non rompe il confronto). Il dodicesimo posto resta libero (vedi dubbio 6).

## 4. Script d'interazione

Convenzioni:
- «visibile» = presente nel DOM e non nascosto (Playwright `is_visible`); attesa massima per ogni atteso 5 s.
- «il file X» = il `file-item` il cui `file-name` ha testo esatto X.
- Ogni passo parte da un server con `data/` vuota (riavvio pulito), fa la preparazione, poi carica
  `http://localhost:8080/`. Passi indipendenti.
- Preparazione **via rotte** (`POST`/`PUT`) fallita -> passo «non valutabile» (fuori dal denominatore). Preparazione
  **via interfaccia** fallita -> passo fallito.
- Le finestre `confirm()` del browser si accettano (Playwright di suo le rifiuterebbe).
- File di prova: `nota.txt` (4 byte, `ciao`), `foto.png` (PNG 1x1), `relazione.pdf` (PDF minimo di una pagina).
- Dati «trio»: A=`nota.txt` con `["work","important"]`, B=`foto.png` con `["work"]`, C=`relazione.pdf` con
  `["personal"]`, creati con `POST` + `PUT`.

## 6. Dubbi e scelte da controllare

1. **Passi 12 e 13 (cancella file, togli etichetta dall'interfaccia)**: il protocollo impone il CRUD nel contratto,
   non dice esplicitamente se vale anche per l'interfaccia. Li ho messi per il «sistema proattivo»; se si legge la
   regola come solo-contratto, si tolgono passi 12-13 e marcatori `file-delete`, `tag-remove` (si torna a 11 passi,
   9 marcatori).
2. **Stato degli screenshot**: il protocollo fa un solo screenshot dopo lo script; dopo il passo 13 resta un solo
   file con una sola etichetta, poco utile per G1/G3. Propongo di fotografare con i dati del trio preparati a parte.
3. **Contenuto del file** (`GET /api/files/{id}/content`): rotta di formato per verificare che il file sia davvero
   salvato, non solo il nome; il testo non chiede di scaricarlo.
4. **Duplicati e maiuscole**: il server toglie i duplicati esatti; `Work` e `work` sono distinte. Lo script usa solo
   minuscole e non manda duplicati nell'interfaccia, quindi non premia ne' punisce scelte diverse; R3 non manda piu'
   duplicati (prima si').
5. **`upload-submit` obbligatorio**: impone un pulsante anche a chi carica appena scelto il file.
6. **Dodicesimo marcatore libero**: candidato `upload-status` (messaggio di esito del caricamento, checklist 0
   «upload status feedback»), ma il testo non lo chiede; non messo.
7. **Passo 11**: richiede che i `filter-tag` nascano dalle etichette esistenti e si aggiornino senza ricaricare
   (implicito in «quick filtering» con etichette libere).
8. Checklist 4-7 (robustezza, funzioni innovative, ridondanze, qualita' del codice) non verificabili da script o
   screenshot: non tradotte.
